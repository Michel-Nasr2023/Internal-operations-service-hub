# ADR-001: Use a Relational Database as the System of Record

**Status:** Accepted and implemented (SQLite via TypeORM)

## 1. Problem

The hub tracks tickets from creation to resolution and links them to users, assignees, comments, attachments, notifications and an audit trail. It must enforce valid state transitions and access rules, and feed queues and dashboards.

## 2. Options

| Option | Summary |
| --- | --- |
| A. Relational database | Tables for each entity, queried and joined by ID |
| B. Document database | Each ticket stored as one document with everything embedded |
| C. Several specialised stores | Tickets, audit and notifications in separate systems kept in sync |

## 3. Decision

**Option A.** A relational database (SQLite, accessed through TypeORM) is the single source of truth.

- Separate tables for users, tickets, comments, attachments, views, notifications, audit log, reset tokens and email outbox (see [data model](../data-model.md)).
- Unique constraints prevent duplicates: one account per email, one notification per recipient and event, one reset token hash.
- JSON columns are used only where the data is always read together with its ticket: the AI result and the ticket's own history.
- File contents are stored on disk under a random name; the database keeps only their metadata.

## 4. Consequences

**Benefits**

- Queues, dashboards, workload and access checks are simple queries.
- Clear, enforceable rules (unique keys, controlled transitions).
- One file to back up during development; the same model moves to PostgreSQL for production.

**Trade-offs**

- SQLite suits a single server; production would use PostgreSQL.
- Foreign-key constraints and optimistic locking (the ticket `version` field) are not enforced yet; consistency is ensured by the service code.
- Files on local disk would move to object storage in production.
